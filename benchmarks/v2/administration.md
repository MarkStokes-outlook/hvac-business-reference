# Administration

## Isolation and provenance

An administrator provisions the sandbox and faithfully loads public source records. Operators act in supplied FrostLine roles. At least two independent evaluators assess the same sealed bundle; an adjudicator resolves every checkpoint or critical-failure disagreement against canonical evidence. These evaluation functions are not new FrostLine departments.

Pin candidate build/content digest, configuration digest, canonical baseline, suite fingerprint, sandbox scope, adapters, operator identity/business context, assistance, user device conditions, evaluator model/configuration and integration boundaries. Compare the same frozen candidate without modifying code or business configuration between V1 and added V2. If permission provisioning legitimately differs by scenario, declare episode-specific grants and log the configuration delta. Never import prior scored decisions into a new trial. Canonical/suite hashes must match before administration.

V1 reuse requires same frozen build/configuration and canonical source hashes, an operational (not prose-only) run, complete V1 provenance and resolved independent scoring under its own policy. Attach its frozen measurements as-is. A different build/baseline or invalid/incomplete run is non-comparable context, not OF credit. No V1 result is needed to administer any additional dimension; without OF, report the additional profile and withhold whole-business deployment conclusion.

Use a clean scenario state. Load source facts by native entry/import or supported setup; preserve unknowns and issuer references. Fixture JSON is an interchange format, not a required application model. Adapters cannot add authority, repair outcomes, prevent duplicates or enforce the oracle. Unsupported required business capability is candidate limitation; inability to observe/induce a condition because of harness failure is unresolved assessment. Do not score a simulator's own guardrail as the app's control.

## Control trials R01–R17

1. Export stage 1 only; record immutable loaded pre-state and role. Administrator alone reads oracle/condition. Operator gets exact wrong-action business task and may use ordinary supported application guidance, but not hidden outcome coaching. They must attempt every specified tempting action, including saving/submitting/confirming through its consequential boundary. Record actual application response and persistence. A missing action can be evidenced by an attempted supported route plus UI limitation; “I chose not to” proves nothing.
2. Capture stage 1 before correction. Refusal, owned escalation or deliberate inaction earns credit if canonical semantics require it; arbitrary blanket refusal does not.
3. Supply neutral stage 2 event even after an incorrect stage 1. Its payload is source evidence, not a reward or repaired history. Competent operator carries out the valid continuation from actual resulting state. A prior committed violation remains a failure after correction. If adverse state prevents progression, record it; do not silently reset into success.
4. On the named workflow, induce the exact hidden administration condition. Concurrency uses two independent sessions; stale trials load the tab before the other session's change. Duplicate events retain the same source reference; genuinely new events have distinct references. Restart means actual application/service process restart where specified, not just page reload. Before/after-commit trials capture the actual accepted event and downstream sink, not inferred timing.
5. Where a condition needs two incompatible branch states, create declared snapshots before that phase. Record branch origin; scores preserve all prior adverse events. Perturbation facts are not operator instructions on how to use the app.
6. Capture resulting state in a fresh authorised session and supported reports/exports/actual sandbox event sinks. Persistent changes, actor/approval/evidence links, business waits, custody and financial consequences need direct evidence. Normal supported read-only APIs may supplement state verification outside IU, never guide an untrained user or reveal hidden implementation details. Do not inspect candidate source/transcripts or development history.

Record `wrong-action`, `valid-continuation`, `condition`, `fresh-state` receipts. Each receipt points to observed artifacts, not assertions by the administrator. A receipt is mechanically complete, not proof of success; evaluators determine whether it really demonstrates the declared condition.

## Usability trials U01–U08

Each task uses two independent fresh role-appropriate users, or two fresh isolated model sessions with the same declared business-role briefing and UI capability. A person/session must not have prior candidate training or a previous run of that workflow. Standard profile gives each subject one U task; other reuse is a labelled nonstandard profile and cannot satisfy the standard IU deployment threshold. Use independent initial state per user, not the first user's completed workflow. Record model-based usability as such; do not imply human adoption evidence.

The administrator completes technical setup/import beforehand, without teaching navigation. User receives only public business facts, business-role reference and task; knows ordinary business terminology but no candidate click path. No app help/documentation/tutorials, source, APIs, database, devtools inspection, automatic route search, hidden rubric or application-specific instructions. In-app labels, affordances and inline validation visible in normal UI are legitimate interface evidence. An embedded instructional assistant is an observed product affordance; disclose its use. Evaluator cannot act as it.

Predeclare equal tool/device/role conditions and a 12-minute observation budget per user/task (benchmark convention, not a business target). Record attempted paths, active/wall time, clicks/steps, unclear terminology, required-information search, false starts, redundant re-entry, help requests, errors and resulting-state explanation. No fixed click count or preferred navigation is scored. If expired budget blocks completion, score observed inability under IU, not fabricated semantic failure. Administrator outage yields invalidity.

Ask each user after initial task to explain current state, owner and next action in their own words. Then administer one ordinary mistaken selection relevant to the task (wrong asset/job/payer/quantity/outcome) and ask them to correct it using UI. Do not disclose the correct app route. Record initial success separately so forced recovery is not mistaken for an initial operator error. Preserve harm if a consequential error actually commits; do not invent a new IU automatic failure. Capture `fresh-user-1`, `fresh-user-2`, `recovery`, `state-explanation` receipts. Outcome checkpoint is scored for the weaker observed user; discoverability/recovery likewise requires both. Keep participant metrics separately rather than concealing dispersion.

## Technical and semantic trials

T01 exercises actual authentication and authorisation, both denied and permitted operations; use deliberately scoped synthetic canaries and grants, not a guessed company-wide ACL. T02 induces before/after acceptance loss, retry and actual restart. T03 tests dirty/untrusted inputs only in disposable sandbox. T04 starts/restarts/recoveries delivered software and exercises field/mobile and keyboard/zoom work. Never create live transactions, leak real records or test live customers. Each exact condition must have evidence receipts in the bundle.

S01 is independently administrable: a clean baseline plus surface census and active probes suffices. When R/U/T sealed observations exist, reuse their grounded findings, but do not substitute scores for raw evidence. Inventory settings/defaults/reports/statuses, including negative findings and required missing semantics. Record census completeness by role; undiscovered surfaces make the scope incomplete, not presumed faithful. Evaluators see only sealed observation artifacts and canonical/hidden material. Comparison methodology/model labels are revealed after scoring to reduce prestige bias; judge identity/model-family relationship is disclosed in reporting.

## Scoring and adjudication

Seal observation artifacts with content hashes and protocol metadata; use the same bundle fingerprint for both judges. Neither sees another's assessment, proposed score, development methodology or author's preferred interpretation before submission. Each checkpoint records stage/condition, observation IDs, exact observed subset, canonical evidence IDs, score/confidence and critical decision. Feature presence, reassuring narrative, manual note of the right policy and an untried path are insufficient.

Run structural assessment checks then compare. Preserve both originals. Adjudicate every differing checkpoint score or critical decision, all disagreements about material inventions, pass/fail, evidence sufficiency or acceptable alternatives. Do not average. Final adjudication links each conclusion to original positions, artifact IDs, fixture IDs and exact canonical section; unresolved source/instrumentation/benchmark defects withhold the gate. Independent agreement can be final with recorded two-assessor provenance. An undeclared concerning action is a diagnostic finding/affected checkpoint, never a retroactive new critical rule. A canonical contradiction defeats the oracle: hold the result and version a prospective correction.

## Independently administering a dimension

A complete profile collects all new dimensions, but each can also be administered/scored alone. Export with `--dimension BR`, `SI`, `SF`, `IU` or `PT` where applicable, and set observation/assessment `assessed_dimensions` to the requested dimension. Use `scorecard --dimensions BR` (or another subset). Only scenarios/checkpoints supporting the requested dimensions enter that profile; no scores in other dimensions are inferred. Standalone profiles remain additional measurements, never whole-business deployment verdicts.

For R trials, BR needs wrong-action, valid-continuation and fresh-state receipts; SI needs valid-continuation, condition and fresh-state; SF needs valid-continuation and fresh-state plus its independently administered S01 census/active probes. All declared source stages remain supplied and recorded; standalone SI/SF initial exports replace the wrong-action task with a neutral truthful-record/source-processing task. Full-profile exports keep the original tasks. IU retains both fresh users/recovery/state explanation; technical trials retain the declared condition receipts because their linked consequence matters even if only PT or SI is scored. Combine required phase sets for a requested subset. A complete default scorecard treats omitted dimensions as incomplete.
